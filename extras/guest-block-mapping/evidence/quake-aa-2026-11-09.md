# Quake 1.06 timedemo stability on this assistant container — 2026-11-09

## Result: large host variability; a small performance claim is not defensible

**Status: actual 48/48 measured, 4/4 warmups and four independent smoke-test demo1 runs passed (969 frames each).** The measured 48-run series used one and the same uninstrumented DOSBox binary, with a fixed deterministic Quake demo and persistent Xvfb. Labels A and B are *intentionally placebo labels*, not changed code.

All 52 timedemo sample FPS values, wall times and throttling event counts are committed in [compact CSV](quake-aa-2026-11-09-compact.csv). The complete 52-row CSV, exact manifest and actually executed Python harness are available separately in the conversation's private downloadable analysis ZIP; no Quake assets or generated JIT code were included.

| Metric, 48 measured runs | Observed |
|---|---:|
| FPS median / mean | 189.15 / 187.725 |
| FPS minimum / maximum | 164.5 / 201.7 |
| FPS p10 / p90 | 175.29 / 197.42 |
| p10-to-p90 spread relative to median | **11.70%** |
| FPS population CV | **4.64%** |
| Median absolute deviation / median | **3.25%** |
| First 24 / last 24 median FPS | 189.95 / 188.70 |
| Quartets of same-binary placebo ABBA | 12 |
| Apparent geometric A/B change from *identical code* | **−2.591%** |
| Descriptive 95% quartet-bootstrap A/B interval | **[−5.093%, −0.080%]** |
| Cgroup throttling during measured runs | 4 events; 207.493 ms combined |

Even the descriptive bootstrap interval excludes zero for **two identical conditions**. This is a concrete *false positive* that shows why a naïve small percentage A/B result on this host cannot establish a JIT optimization. The bootstrap interval itself may be miscalibrated due to correlated load or drift; it does not justify a 95% formal false-positive probability claim. First-half/second-half median difference is only −0.66%, but substantial within-half dispersion remains.

The four smoke-test runs before the measured series produced 196.4, 188.4, 181.3 and 170.0 FPS, also with 969 frames each. Their monotonic decline was not a general trend: the 48-run series includes rebounds to >200 FPS.

## Implication for H1–H5

There is currently **no credible evidence that a 1–3% FPS difference is attributable to changing JIT code on this host**. Even a 2.6% fake change appeared without any change. For code correctness and native hot-path identification this host remains useful; for small FPS regressions use a dedicated stable machine, or at minimum build true matched A/B binaries and run many interleaved repetitions while measuring an A/A control and host interference.

Do not change H1's TLB lowering, H2's Z-buffer lowering or H3's surface loop based only on this measurement. PR #5's 161 actual sampled native RIPs and the remaining 44% un-attributed non-JIT sample pool still favor finer helper/caller source attribution *as research*, **not** a measured optimization.

## Follow-up: CPU pinning did not stabilize the host

A separate controlled A/A series pinned the entire DOSBox process to
virtual CPU 0 and persistent Xvfb to virtual CPU 1 via `taskset`.
The executable, Quake 1.06 assets, 969-frame oracle, renderer, config,
fresh-game-per-run policy and ABBA placebo design remained unchanged.
There were four warmups and **24/24 valid measured runs** (six A/A
quartets). Per-run observations:
[quake-aa-pinned-2026-11-09-compact.csv](quake-aa-pinned-2026-11-09-compact.csv).

| Metric | Unpinned (48 runs) | Pinned (24 runs) |
|---|---:|---:|
| Median FPS | 189.15 | 169.45 |
| FPS minimum / maximum | 164.5 / 201.7 | 151.4 / 184.7 |
| FPS p10 / p90 | 175.29 / 197.42 | 154.60 / 178.03 |
| FPS CV | 4.64% | **5.31%** |
| p10–p90 spread relative to median | 11.70% | **13.83%** |
| A/A placebo geometric difference | −2.59% | −1.84% |
| Descriptive quartet-bootstrap 95% interval | [−5.09%, −0.08%] | [−4.29%, +1.44%] |
| First / second half median FPS | 189.95 / 188.70 | 174.35 / 165.35 |
| Cgroup throttling | 4 events / 207.49 ms | 3 events / 77.71 ms |

The pinned series is shorter and was run later, so this is a
diagnostic comparison rather than randomized causal evidence.
Whole-process pinning reduces throughput by limiting the emulator
to a single virtual CPU; it **did not improve dispersion**.
Both observed CV and p10–p90 spread increased. The false A/A
difference remains of order 1–2%, with a wide uncertainty interval.

**Decision:** Do not use simple whole-process `taskset` pinning
as the precision benchmark protocol. Continue hot-path and correctness
investigation in this container, but validate small performance changes
on a dedicated low-noise host or through substantially stronger
interleaved true A/B and placebo controls.
